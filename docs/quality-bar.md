# Starter 质量标准

## 定位

TS App Starter 的目标是成为“优秀的轻量级 TypeScript 应用标准起步工程”。

这里的优秀，不是预置最多能力，而是在保持无业务、无领域、无产品、无平台绑定的前提下，把新应用最容易反复踩坑的工程基础做得可靠、可验证、可升级。

Starter 只负责：

- 运行环境与版本约束；
- API、Worker、前端和数据库的最小工程结构；
- 本地开发、测试、构建、Docker 和 CI/CD 基线；
- 明确的模块边界、配置边界和升级机制；
- 可重复验证的项目生成与部署流程。

Starter 不负责认证、权限、支付、邮件、缓存、队列、对象存储、UI 组件库或任何行业业务能力。这些能力应由具体应用或独立维护的公共 package 按真实复用情况引入。

## 优秀的验收标准

### 可靠生成

通过 CLI 创建的项目可以独立安装、检查、测试、构建、启动和部署；生成结果不残留模板身份、版本或内部开发文件。Demo 仓库用于持续验证从 `npx` 到部署的完整链路。

### 可验证工程

Starter 自身和生成项目都应有清晰的 format、lint、typecheck、test、build、migration、health 与 Docker smoke 检查。每项检查失败时都应能定位到具体原因，而不是静默放过风险。

### 可控升级

Starter 与 CLI 版本明确对应，变更记录和升级说明持续维护。应用创建后独立演进，不要求自动同步模板；需要吸收基础设施改进时，有可审查、可回滚的升级路径。

### 清晰边界

默认结构支持模块化单体，但不预留教育、零售、平台或其他具体领域的专用模块。公共代码只有在跨应用复用事实充分、依赖方向稳定、API 可以独立解释时，才应抽成 package。

### 生产基线

默认交付路径应具备非 root 容器、健康检查、数据库迁移、日志、最小权限和 CI 构建发布能力；更重的可观测性、云厂商服务和分布式设施按应用实际需求加入。

## 长期判断原则

每次新增能力都要回答三个问题：

1. 它是否属于所有标准 TypeScript Web 应用都需要的工程基础？
2. 不加入它，是否会导致生成项目无法可靠开发、测试或部署？
3. 它是否会引入某个业务领域、供应商、部署平台或产品决策？

前两个问题都回答“是”、第三个问题回答“否”，才适合进入 Starter。否则，应留在具体应用或独立 package 中。
